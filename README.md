# ANTA: Autonomous Network Threat Analyzer

ANTA is a packet capture and analysis pipeline that finds command-and-control beaconing, remote-access trojans, malware downloads, DNS tunneling, data exfiltration, ARP spoofing (LAN man-in-the-middle), port and host scanning, and algorithmic C2-domain generation from traffic *behaviour* (timing, sizes, entropy, asymmetry, destination rarity, what a file or protocol really is) instead of signatures. For each incident it also works out who the victim is: IP and MAC address, host name, Windows user account and domain. Around that it keeps a passive inventory of every device (operating system, IoT, services), knows where each internet address is registered, checks traffic against published threat-intelligence feeds, describes what encrypted sessions are doing without decrypting them, and learns each host's normal traffic so it can flag a sudden change.

```
 NIC / pcap ──► C++ engine ───────────────► Python analyzer ─────────────► Web dashboard
                libpcap or AF_PACKET ring    features + detectors          WebSocket feed
                L2-L4 dissectors             Isolation Forest (ONNX)       explanations, charts
                TCP reassembly               natural-language explainer    per-stream .pcap export
                DNS / HTTP / TLS (JA3/JA4)
                      │ ZeroMQ PUSH→PULL (ZMTP 3.0)  ·  or newline JSON over a Unix socket / stdout→stdin
```

## Desktop app (macOS, Windows, Linux)

ANTA ships as a normal desktop application, so no terminal is needed. It is laid out like the analysis tools analysts already know, Wireshark and Ghidra: a menu bar (File, View, Capture, Analyze, Statistics, Detection, Help, all keyboard-navigable), a short toolbar (**Open…**, **Live capture…**, **Stop**, **Save…**, the **command bar** and the **Detector** switcher; everything else is in the menus), five notebook tabs (**Alerts**, **Packets**, **Statistics**, **Hosts**, **Files**), and framed panes on gray window chrome: a sortable alert table above the selected alert's explanation and its stream, Wireshark's three packet panes, and so on, with a status bar of counters at the bottom.

- **Pop-out windows.** Every pane's title bar has ⧉: it opens that pane in a window of its own (a statistics table or the I/O graph, one alert's charts, the network map, the packet list…), kept live, so several can sit side by side or on another screen. **View → Open this view in a new window** does the same for the whole tab. A window shows its data as soon as it opens, with what the pane was showing (a statistics tool's filter, the TCP stream or flow graph, and the focus, if one is on); its bar has **⟳ Refresh** (F5 or Ctrl/⌘+R, which refresh the view in the main window too) and, on a focus, **Whole capture**.
- **For beginners.** Every pane's title bar also has **?**, a short plain-language note on what the pane shows and how to use it; **Help → Getting started** walks through the first steps, and with no capture open the start screen offers opening a file, a live capture or the demo. **Help → Protocols** explains every protocol ANTA reads (about 55, grouped from how packets get around to Windows networks and databases) in plain words: what it is, what it looks like in a capture, what to look out for, and filters to try on the open capture with one click. It shows how many packets of each the capture holds (and can list only those), finds a protocol by name, port or word, and is a click away wherever protocols appear: the **?** beside each layer in the packet details, **What is …?** at the top of a packet's right-click menu, and the protocol rows in Statistics.

Your data stays in a private per-user folder: `~/Library/Application Support/ANTA` on macOS, `%LOCALAPPDATA%\ANTA` on Windows, `~/.local/share/anta` on Linux.
- `captures/` holds recordings of live sessions, as a rolling buffer of segments. Export uses them.
- `flows/` holds the flow logs (one JSON line per connection, one file per day), `intel/` the threat-intelligence feeds you downloaded or imported, `geo/` a GeoIP table you downloaded (the bundled one is used otherwise), and `settings.json` the Settings dialog's choices. All are owner-only.
- `samples/` holds the generated demo capture.
- `logs/` holds the app log.
- An optional `anta.toml` configures thresholds and allowlists (see `config.example.toml`).
- An optional `models/` folder holds a model you trained yourself; it overrides the bundled one.

### Packet viewer

The **Packets** tab works like Wireshark's main window: a packet list with No., Time, Source, Destination, Protocol, Length and Info, a layer tree, and a hex/ASCII dump.
- **Same rows as Wireshark:** the packet list reproduces Wireshark 4.6's Source, Destination, Protocol, Length and Info columns. Checked row by row with `tshark` on real and synthetic captures (1.2 million frames, including heavy reordering, loss and sequence wraparound), every row is identical. On a real Active Directory capture (42,497 frames of LDAP, SMB2, DCE/RPC, Kerberos, QUIC and TLS), 42,496 rows are identical in both views; the one difference is a call Wireshark's own LSARPC parser marks `[Malformed Packet]`.
  - TCP analysis follows Wireshark's rules exactly: relative sequence numbers, window scaling, `[TCP Retransmission]`, `[TCP Out-Of-Order]`, `[TCP Dup ACK N#M]`, `[TCP Window Full]`, keep-alives, zero windows and the rest, in Wireshark's order.
  - Messages split across segments (TLS records, HTTP bodies, SSH packets, DNS over TCP) are reassembled the way Wireshark does it. Earlier pieces read `[TCP PDU reassembled in N]`; the frame that completes the message shows it. IP fragments are reassembled too.
  - Files are decoded in two passes, like Wireshark opening a file, so cross-references to later frames appear: `(reply in N)` on pings, `[Reassembled in #N]` on fragments, and the negotiated TLS/SSH version on every frame of a session. Live captures show the single-pass view Wireshark shows while capturing.
- **Decoded protocols:** Ethernet, 802.1Q/QinQ, MPLS, PPPoE, Linux cooked (SLL/SLL2), 802.11/Radiotap, PPP, GRE/ERSPAN, VXLAN, Geneve, ARP, IPv4/IPv6 (extension headers and fragments included), TCP, UDP, ICMP/ICMPv6, IGMP, DNS/mDNS/LLMNR, DHCP/DHCPv6, NBNS, NetBIOS datagrams and the Windows browser protocol, Kerberos (UDP and TCP, and inside SPNEGO/GSS-API logons), NTP, SSDP, TLS (every record type, SSLv2 and PCT; Client Hello with SNI, ALPN, JA3 and JA4), QUIC (Initial packets are decrypted, as Wireshark does with keys derived from the connection ID: their frames, the server name and JA4), DTLS 1.0, 1.2 and 1.3 over UDP (found by Wireshark's heuristic; the Protocol column follows the version as Wireshark settles it, handshake messages are reassembled from their fragments, and the Client Hello gives the server name, JA3 and JA4; the records themselves stay encrypted), HTTP (including OCSP, CRL, JSON and image bodies; each response linked to its request, with the request's URI and the response time, as `http.request_in` and `http.time`), SSH, FTP and FTP data, SMTP, POP, IMAP, Telnet, LLDP and STP.
  - DTLS was checked on real OpenSSL DTLS 1.0 and 1.2 sessions (`tests/fixtures/dtls`, reproducible with `python -m anta.tools.tls_record`), on the same sessions with datagrams lost, repeated and reordered and run back to back on the same ports, and on a DTLS 1.3 exchange: the packet list matches Wireshark's on every frame in both views, the `dtls.*` filters select the same frames, and JA3 and JA4 equal Wireshark's.
  - **Databases:** MySQL/MariaDB (greeting, login, commands, OK/error replies and result sets, prepared statements, the switch to TLS), PostgreSQL (every message type, errors with their SQLSTATE code, the switch to TLS) and Microsoft SQL Server's TDS (packet types, SQL batches, the errors and messages a response starts with, TLS inside pre-login). Info columns and the `mysql.*`, `pgsql.*` and `tds.*` fields match Wireshark, so `mysql.error_code || pgsql.type == "Error" || tds.error` finds every failed query.
  - **Windows domains:** LDAP and CLDAP (searches, binds, SASL-encrypted traffic, a domain controller's own description in its CLDAP ping replies), SMB2/SMB3 over the NetBIOS session service (trees, files, reads and writes, errors, compounds; SMB1's negotiation), NTLMSSP (the user, domain and machine of an NTLM logon), and DCE/RPC with 31 Windows interfaces named the way Wireshark names them (SAMR, LSARPC, NETLOGON, DRSUAPI, SVCCTL, the task scheduler, the print spooler, WMI, DCOM and more), over TCP and SMB named pipes, with the endpoint mapper's port lookups.
  - MAC vendor names cover the IEEE assignments of 76 common hardware vendors (11,645 prefixes) under Wireshark's short names. Windows status codes, file-system controls and RPC operation names are Microsoft's, as Wireshark lists them (`anta/tools/gen_oui.py` and `gen_names.py` regenerate the tables from an installed Wireshark).
- **Byte highlighting:** clicking a layer or field highlights its bytes in the hex dump.
- **Files:** a capture of any size is paged 200 packets at a time and never loaded into memory, with match counts for every filter.
- **Live captures and the demo replay:** packets stream in with **Follow live** (rate-limited to 400 per second in the engine, so floods can't overwhelm the UI). Because live captures are recorded, any packet, including ones older than the stream, opens in full detail. Frame numbers stay correct across recording rotation.
- **From an alert:** **Show packets** in the stream panel opens the Packets tab filtered to exactly that alert's flows.
- **Decrypt your own TLS:** **Decrypt TLS…** in the Packets tab loads a TLS key log (the `SSLKEYLOGFILE` a browser or `curl` writes), and the packet view then shows the decrypted records — the same thing Wireshark's *tls.keylog_file* does, and only for traffic you already hold the keys for. ANTA decrypts all five TLS 1.3 suites (AES-GCM, ChaCha20-Poly1305, AES-CCM and AES-CCM_8, from the `*_TRAFFIC_SECRET_0` lines), and SSL 3.0 and TLS 1.0, 1.1 and 1.2 with the AEAD suites (AES-GCM, ARIA-GCM, Camellia-GCM, AES-CCM and CCM_8, ChaCha20-Poly1305), the CBC suites (AES, Camellia, ARIA, SEED and Triple DES, with SHA-1, SHA-256 or SHA-384 MACs, MAC-then-encrypt or encrypt-then-MAC), RC4 and the NULL (MAC-only) suites, whatever the key exchange (RSA, DHE, ECDHE, PSK), and shows each record's plaintext. The key log may give the master secret (`CLIENT_RANDOM`) or only the premaster secret (`PMS_CLIENT_RANDOM`, or an RSA key exchange's `RSA` line, keyed by the encrypted premaster's first bytes); ANTA then computes the master secret as the protocol does, over the handshake transcript when the extended master secret (RFC 7627) is in use. The block ciphers' tables are read from their RFCs by `anta/tools/gen_cipher_tables.py`, and each cipher matches its specification's test vectors and OpenSSL on thousands of random inputs. Wireshark 4.6 can't decrypt the ARIA suites; ANTA can, so on those sessions its packet list shows the plaintext where Wireshark's stays encrypted. It follows a connection through TLS 1.3 key updates from either side, TLS 1.2 renegotiations started by either side (the renegotiating handshake, read under the old keys, is listed like a plaintext one, and each side moves to the new keys at its own Change Cipher Spec), and TLS 1.3 early data on a resumed session (from `CLIENT_EARLY_TRAFFIC_SECRET`, up to the End of Early Data). Real OpenSSL sessions of each kind are in `tests/fixtures/tls_suites` (reproducible with `python -m anta.tools.tls_record`); on every one the packet list matches Wireshark's in both views, and the session analysis reads every HTTP message in them, after each re-key. A response read until the connection closes completes where Wireshark completes it: at the close_notify when it shares the response's TCP segment, else at the FIN. HTTP/1.x inside it is dissected as Wireshark dissects it: a message spanning several records is reassembled and shown in the frame that completes it (the frames before read *[TLS segment of a reassembled PDU]*, with `tls.reassembled_in`), and the `http.*` fields and filters work on it (`http.request.full_uri` reads `https://…`). The HTTP inside goes further than the packet view: the **Files** tab lists and saves downloads from those HTTPS sessions (marked HTTPS), and the detectors read it as they read plain HTTP — a program or script downloaded over HTTPS raises the download alert, and threat-feed URLs and file hashes are matched inside it. A key log loaded after a capture was analysed re-reads that capture with the keys and checks the sessions it opens up; a capture opened while keys are loaded is analysed decrypted from the start. On a test lab built to make this hard (chunked bodies cut across records, pipelined messages sharing a record, gzip, a body that runs until close_notify, a 100 KB download in full-size records over many TCP segments, a key log holding only the server's secret), the packet list matches Wireshark's on every frame and every file hashes to the bytes the server sent. **HTTP/2** (what browsers and curl usually negotiate) is read the same way, inside decrypted TLS and as cleartext h2c: HPACK header compression (Huffman strings, the dynamic table) is decoded, each stream's request and response paired, and response bodies — interleaved across streams, padded, gzip — hashed and listed in Files, so downloads over HTTP/2 raise the same alerts. The packet view dissects it as Wireshark does (Info such as `HEADERS[1]: GET /path` and `DATA[1] (text/html)`, the `http2.*` fields and filters), and with the handshake secrets a browser's or curl's key log holds, the TLS 1.3 handshake itself is decrypted (Encrypted Extensions, Certificate, Finished), as in Wireshark. This was checked on real traffic — curl's HTTP/2 client recorded on loopback (`tests/fixtures/h2_curl.pcap`, reproducible with `python -m anta.tools.h2_record`) — and on a lab covering CONTINUATION, server push, 103, trailers, PING, RST_STREAM, priority and frames cut across records: the packet list matches Wireshark on every frame and 43 HTTP/2 fields match value for value, and HPACK decodes RFC 7541's own examples. If the capture missed bytes inside an HTTPS connection, decryption picks up again at the next TLS record (the file the gap cut is marked incomplete; HTTP/1.x requests and responses after it are read as before). For every one of those suites, on a capture and key log that Wireshark decrypts, ANTA decrypts the same records to byte-identical plaintext; the cryptography (SHA-1, SHA-384, AES-256, AES decryption for CBC, GCM, CCM, ChaCha20-Poly1305, the TLS 1.0 and 1.2 PRFs) is checked against the published RFC, FIPS and NIST test vectors. The key log is kept owner-only in the private runtime folder, never logged, and removed when you clear it or the app exits.

### Filtering, coloring and following streams

- **Tools ▾** beside the filter box holds the packet list's options in one menu: filter templates, colorizing and the coloring rules, host names, the time display and time shift, Find, Go to, Save packets and TLS decryption. Its **Filter templates** apply one of 28 one-click filters, in four groups: connection problems (TCP problems, retransmissions, lost segments, zero windows, resets, connection attempts, ICMP errors, fragments), application errors (database errors, HTTP errors, DNS failures, slow DNS and slow web responses, TLS alerts, login failures across Kerberos/LDAP/SMB/FTP/HTTP/MySQL/PostgreSQL, SMB errors, malformed packets), noise (broadcast, multicast, discovery chatter, and everything but those) and hunting (logins and user names, plain-text web requests, program downloads, TLS server names, DNS queries, remote access, database traffic). Hovering one shows what it finds and its filter. Each is Wireshark syntax and selects the same frames `tshark` selects on the bundled captures and on two real exercise captures (the one exception: a `[Malformed Packet]` from Wireshark's LSARPC parser).
- **Display filters** use Wireshark's language: `ip.addr == 10.0.0.0/8 && tcp.port in {80, 443, 8000..8100}`, `http.request.uri matches "(?i)login"`, `frame contains "GET"`, slices like `tcp[13] & 0x12 == 0x12`, `!(arp || dns)`. The box turns green or red as you type, with Wireshark's error message, and suggests field names. Recent and saved filters stay in your browser. The selector next to it switches to a BPF **capture filter** (`host 10.0.0.23 and tcp port 443`).
  - Over 400 fields are supported, including Wireshark's expert fields (`tcp.analysis.*`, `tcp.connection.*`, `dns.retransmit_request`, `icmp.resp_not_found`, `ip.ttl.too_small`, …) and the Windows domain protocols (`kerberos.CNameString`, `ntlmssp.auth.username`, `smb2.filename`, `ldap.*`, `dcerpc.*`, `drsuapi.opnum`, …). Set elements need commas, as Wireshark 4.6 requires (`{80 443}` is refused with Wireshark's message). On the bundled captures and a real home capture, 187 test filters (the coloring rules included) select exactly the frames `tshark -2` selects; on the Active Directory capture, all but two (`_ws.expert` on the LSARPC call Wireshark marks malformed, and `tls` on one frame where Wireshark keeps an unfinished TLS fragment after a reassembled message).
  - Every packet's fields are listed under **Filter fields** in the detail pane. Right-click any field, packet or statistics row to **Apply as filter**, **Prepare as filter**, combine it with the current filter (and / or / and not), or copy it.
- **Coloring rules** start as Wireshark's default rules (Bad TCP, TCP SYN/FIN, ARP, ICMP, HTTP, UDP, …), so rows have the colors Wireshark shows. **Coloring rules…** edits, reorders, disables and adds rules; the first match wins. Rules are saved owner-only in your data folder and validated before saving. **Colorize conversation** (right-click a packet) colors one conversation for the session, ahead of the saved rules.
- **Follow TCP/UDP stream** shows a conversation's payload in order, client and server in two colors, as ASCII, hex or raw bytes, either direction or both, and filters the list to that stream. With a TLS key log loaded, its **View** menu also offers the decrypted TLS application data and each HTTP/2 stream inside it (header lines, then the body, decompressed if it was gzip or deflate), as Wireshark's Follow TLS Stream and Follow HTTP/2 Stream show them; both were checked byte for byte against tshark on every stream of the test captures.
- **Mark packets** (Ctrl+M), **Go to packet** (Ctrl+G) and time display formats (seconds since start, since previous packet, absolute, UTC, epoch) work as in Wireshark.
- **Select several packets and analyse just those.** Drag across rows, Shift-click (or Shift+↑/↓) for a range, Ctrl-click (⌘-click on a Mac) to add or remove one, Ctrl/⌘+A for every packet the list shows; double-click an address for every packet involving it, or elsewhere in a row for the conversation between its two ends. The list's title bar then counts them and offers what to do with them, as does a right-click on the selection:
  - **Focus on these**: every view (the packet list, Statistics, Hosts, Files, the alerts and their stories) shows only those packets, the connections they belong to and the alerts about them. A bar across the window says so, with the steps taken (*Whole capture › 1,696 packets involving 10.0.0.23 › 12 selected packets*); select within a focus to narrow it again. **Back** (or Esc) retraces one step and **Whole capture** returns at once, each to the packet list exactly as it was (its filter, page and selected packet). The Analyze menu has the same.
  - **Analysis tools ▸** opens any Statistics tool (conversations, endpoints, protocol hierarchy, I/O graph, flow graph, expert information, DNS, HTTP, TLS, fingerprints, cleartext logins, rhythm, encrypted traffic, countries) on the selection in a small window over the page, without changing anything else; open several side by side to compare, drag them by the title, resize them by the corner. On a single packet the same submenu works on its conversation.
  - **Explain…** puts the selection in plain words (as Explain does a connection), and **Explain with AI…** asks the AI model set up under Detection… (Claude, OpenAI, Gemini or a model on this computer). It first shows exactly what would be sent: one summary line per packet as the list shows it, the selection's statistics, ANTA's own findings and the alerts about it, never packet contents, with passwords, logins' secrets, query strings and cookies removed and internal addresses and MACs replaced (internal-host-1, mac-1 … unless you allowed sharing them, and put back in the answer). The answer says what the packets show and how sure it is, cites the frames each point rests on (click to open them) and suggests what to check next.
  - Save, mark (Ctrl+M) or copy the selection as a display filter. A selection is kept on the server as a filter of frame-number ranges, so it can be thousands of separate packets; a long one reaches the engine through a private file rather than the command line.
- **Find…** (Ctrl+F) finds the next or previous packet by a display filter, text in the packet list or anywhere in the detail tree, hex bytes or a regular expression, within what the list shows, as Wireshark's Find Packet does.
- **Apply as column** (right-click a field, or the column header menu) adds any field as a packet-list column, up to 12. **Set as time reference** (right-click a packet) makes times count from that packet, and **Time shift…** moves every packet's time, or sets one packet's time, for display. **Host names** shows the names the capture gives addresses (DNS answers, and the names hosts announce over NetBIOS, DHCP, mDNS and the like) in place of the addresses; nothing is looked up outside the capture.

### Statistics

The **Statistics** tab has Wireshark's analysis tools, computed over the whole file or only the packets matching a display filter:
- **Capture properties:** packets, bytes, duration and average rates (as `capinfos` reports them).
- **Protocol hierarchy:** packets and bytes per protocol, nested as in Wireshark.
- **Conversations** and **Endpoints** for Ethernet, IPv4, IPv6, TCP and UDP, with packets and bytes sent and received per address, a **Top talkers** chart, and each address's role from the network map.
- **I/O graph:** packets, bytes or bits per interval, the TCP error rate, and up to two extra graphs from display filters. Click an interval to see its packets; a table view is included.
- **Packet lengths**, **Expert information** (errors, warnings, notes and chats grouped as Wireshark's Expert Information dialog groups them, each linking to its frames), **DNS** (names, types, response codes, the request-to-response times and the slowest responses), **HTTP** (hosts, URLs, methods, status codes, user agents, content types) and **TLS** (server names, JA3 and JA4 fingerprints, versions).
- **TLS fingerprints:** every client fingerprint (JA4, with the JA3 variants it came with: Chrome shuffles its extensions, so one browser has one JA4 and many JA3s), the hosts that sent it, the server names it asked for, and any feed that lists it; and every server fingerprint (JA4S, JA3S) with the servers that answered with it. A rare fingerprint used by one host is worth a look.
- **Encrypted traffic:** what each encrypted session (TLS, QUIC, SSH, VPNs, and any high-entropy stream) is most likely doing, from its packet sizes, direction and timing alone: handshake only, web browsing, bulk download or upload, media streaming, a call, an interactive remote session, a periodic heartbeat, an idle kept-open connection. Each verdict states its evidence ("12 MB sent, 40 KB received: 99% upstream").
- **Countries & networks:** traffic per country and per autonomous system (the network's owner), from the offline GeoIP table. A rare network moving a lot of data stands out; one click filters to its addresses.
- **Flow graph:** who sent what to whom, in order, like Wireshark's: one lane per address, one arrow per packet with its ports and Info; click an arrow to open the packet. **TCP stream graphs:** one direction of a TCP stream as Wireshark draws it (Stevens sequence numbers, throughput, round-trip time, window scaling), with a crosshair and tooltip; click a point to open its packet.
- **Rhythm:** when each device talked to each server (a channel: client, server and port) over the whole capture, one row each, with time across and a darker cell where it checked in more. People browse in bursts; software calling home does it on a timer, which shows as evenly spaced stripes. Rows are sorted steadiest first, each with its period ("every 4.2 s ±1%") and how steady it is (the beacon detector's own timing score); a channel raised as a beacon shows its alert, and a timer many devices keep with one server (a cloud service's keep-alive) is marked *shared ×N*. Click a row for the gaps between its check-ins (a timer draws a flat line); right-click for its packets; a table view is included.
- **Cleartext logins:** every login whose password crossed the network readable, like Wireshark's *Tools → Credentials*, but without the password: ANTA reads FTP and POP `USER`/`PASS`, IMAP `LOGIN`, SMTP and POP `AUTH PLAIN`/`LOGIN`, HTTP Basic authentication and login forms, LDAP simple binds, Telnet login prompts and SNMP community strings, and lists the service, the account, how often, whether the server accepted it, and the encrypted form to move the service to (SFTP, IMAPS, LDAPS, SSH, SNMPv3, …). The engine reads a password only to know one was sent and drops it at once; it never appears in any record, alert or report. Each client-server-service pair also raises a medium **Password Sent in Clear Text** alert (anonymous FTP, which has no real password, is listed but not alerted).

Endpoints, conversations, packet lengths, capture properties and every Expert Information entry match `tshark -z` on the bundled captures and on a real capture.

### Hosts: table and network map

The **Hosts** tab shows the devices two ways, switched with **Table / Map** at its left; the host picked in one stays picked in the other. Clicking an address anywhere else (an alert, a packet's address menu, a story, a Statistics row, an Ask answer, the first-look list) opens the **host panel** at the right instead: what the host is (name, device, OS, MAC, when seen, traffic, services, location), who it talked to (each row opens their packets, each address opens its own panel), its alerts, files and clear-text logins, with **Show its packets**, **Focus on it**, **Explain…**, **In Hosts**, **On the map** and **📌 Pin** to the investigation.

**Focusing the map.** Clicking a host on the map (or right-clicking it, or Enter on the selected host) opens a menu: **See its packets** (or only what it sent, only what was sent to it, or what passed between it and the other focused hosts), **Focus on this**, **Focus on this + what it talks to and what talks to it** (that host and every host it exchanged traffic with, either way, with how many that is), **Host details** and **Copy address**. A focus lights its hosts and their conversations up while the rest of the map fades right back, still in place (hover a faded host to see it again, click it to add it). Focus on as many hosts as you like: **Shift-click** a host to add it to the focus or take it out, or from its menu **Add it to the focus** (alone or with what it talks with), light up or stop lighting up what a focused host talks with, remove it, or **Focus on only this**. The strip over the map names what it is focused on (× removes one), how many hosts are lit, **Zoom to them** and **Clear the focus**; focused hosts get a blue halo. Hosts past *Show top* join the map when the focus lights them up, and replay arrows outside the focus fade too. The host details beside the map have the same choices under **Focus ▾**, and the host panel has **Map of who it talks with**. The map's focus stays while you change the app's focus and is cleared when another capture opens.

**⏱ Replay** (in the map's bar; *View → Replay the capture on the map*, or type `replay`) is a time machine for the capture. It plays any stretch of it: the whole capture, or **From**/**to** times you type (a clock time like `10:03:40` in your time zone, `+3:40` or `+220` from the start, or `3m40s`) or Shift-drag on the scrubber; **Go to** jumps to a moment, and clicking or dragging the scrubber moves through it (← → step, Space plays). The speed is a multiple of the speed the traffic was captured at: **1×** plays it as it happened, with presets from 0.01× to 100× and **Custom…** for any multiple you type (`0.3`, `2x`, `1/20`, up to 10000×); the bar under it says how long the stretch takes at that speed. A live capture's timeline is read again when you play it after it grew or stopped. Each packet flies across the map as an arrow from its sender to its receiver, red when the two are in an alert; when more packets are in flight than can be read, it draws one arrow per conversation sized by how many packets it carried, and says so (slow down to see each one). The scrubber shows the traffic over time (the engine's exact counts) with a mark where each alert was raised; the map lights the hosts and conversations active in the last 10 seconds, minute or 5 minutes (or everything so far) and rings the hosts whose alerts have been raised by then, and a strip under it names those alerts (click one to open it). It follows the focus, like every view.

The map draws every host and the conversations between them, and labels what each address probably is: router or gateway, DNS or DHCP server, a server by the services it answered (web, mail, SSH, FTP, file, database…), client device, internet host, broadcast or multicast group. Each role has its own color and shape, and node size follows traffic.
- Click a host to see **why it got its label** (the evidence: answered DNS queries, announced as router by DHCP, a MAC carrying traffic for many addresses, ports it listened on), its names (DHCP, NetBIOS, mDNS, DNS, TLS SNI, HTTP Host), vendor, a guessed OS with the reason, and its busiest conversations. One click shows its packets or the packets it sent.
- **Grouped** layout puts broadcast and multicast, the local network, gateways and the internet in columns; **Force** layout clusters hosts by who talks to whom. Pan, zoom, drag nodes, search and show the top N hosts; **Table** lists them.
- Windows networks: the **domain controller** is recognised from the Kerberos logons it answers, and each machine shows the user accounts that logged on from it and its domain.
- Hosts involved in a high or critical alert get a dashed ring and a ⚠ in their label, and their details list the alerts.
- Internet hosts show their **network owner and country** (AS number and name, from the offline GeoIP table), as do the hosts in alerts.
- It only claims what the capture shows. In a capture taken on a router, the router's MAC is not credited to the hosts it forwards for.

The table is a passive inventory: every device the capture shows, what it most likely is, and why, from listening alone (nothing is sent to any device).
- **Operating system** from independent fingerprints, each weighed: the shape of its TCP SYN (initial TTL, window, MSS, window scale and option order, as p0f reads them), its DHCP client's parameter request list (option 55) and vendor class (option 60), Windows browser announcements, HTTP User-Agents, and, weakest, the IP TTL alone. Fingerprints tied to a MAC are only credited when the MAC is the host's own (a router's MAC carries many addresses).
- **IoT devices** from their maker (MAC vendor), the services they announce over mDNS (Chromecast, HomeKit, Hue, Sonos, printers…), their host names, embedded DHCP clients and IoT protocols (MQTT, CoAP, Tuya). Printers are recognised from their ports and mDNS services.
- **Services** each device offers, **applications** it uses and serves (from payload identification, below), names, MAC addresses and vendor, user accounts and domain, traffic, the alerts it is in, and for internet hosts the network owner and country.
- Filter to this network, IoT devices or internet hosts; search; open a device's evidence; jump to its packets or the map; export the inventory as CSV.

### Investigating an incident

Clicking a row of the alert table opens what ANTA found and why, plus:
- **File:** for a download, its name, URL, type (from its first bytes, whatever the URL or `Content-Type` claim), size and **SHA-256** (copy it into VirusTotal or a sandbox). Bodies sent chunked or gzip/deflate-compressed are decoded first, so the hash is the file's, exactly as Wireshark's *File → Export Objects → HTTP* computes it. Files copied over SMB2 (read from or written to a Windows share) are hashed the same way, matching *Export Objects → SMB*, and so are files sent over FTP (passive or active mode, including through a server behind NAT whose `227` reply names an address that isn't on the wire), matching *Export Objects → FTP-DATA*.
- **Affected host:** the local machine's IP, **MAC address**, **host name**, **Windows user account**, **domain** and operating system. These come from the capture itself: Kerberos and NTLM logons (the user and machine accounts, the domain), Windows browser announcements (the computer name and Windows version), a domain controller's CLDAP replies, the server names in SMB share paths, DHCP and NetBIOS registrations. **Show on network map** jumps to it.
- **Device:** when a device's configuration crosses the network in the clear (a router backup uploaded over FTP, say), ANTA reads it and lists every address the device has, loopback and point-to-point links included, with the interface each belongs to. OpenWrt, Cisco IOS, Juniper, MikroTik and dnsmasq configurations are understood, as are Linux (`ip addr`, `ifconfig`, ifupdown, netplan) and Windows (`ipconfig`) output. Every alert about any of those addresses shows the device, and the network map labels its node as that device. When that device is the one acting maliciously (the resolver poisoning answers, or a host beaconing, running a remote-access channel or sending hand-built packets), a critical **Compromised Device** alert names it, and its row in the alert table lists every address assigned to it.
- **Verdict and notes:** mark each alert New, Investigating, Confirmed or False positive and write what you checked. The verdict shows in the alert table (a dismissed alert is struck through), survives the alert being updated, and goes into the report; a false positive names no victim, device or indicator there.
- **Ignoring a noisy source.** A central router, a monitoring server or a scanner you run yourself can raise the same alerts over and over. **Ignore its source ▾** (beside an alert's verdict, or *Ignore its source* when you right-click an alert) ignores that kind of alert from that address, or every alert from it; *Detection → Ignored alert sources…* (or the **N ignored** chip on the alert bar, **Ignore its alerts…** in the host panel, or type `ignored`) lists the rules, adds one by hand (an address, a network such as `10.0.0.0/24`, or a MAC address, for one kind of alert or every kind, with a note) and has **Stop ignoring**. An alert is ignored when its source address or the device it blames matches; alerts *to* that address still show. Ignored alerts are set aside, not deleted: they leave the alert list, the stories, the map and *What to look at first* at once, the chip counts them, and stopping a rule brings them back with their verdicts and notes. The rules are saved owner-only in the data folder (`ignored-sources.json`) and apply to every capture.
- **Incident report** (above the alert table) gathers the malicious devices (with all their addresses), every affected host, every alert with its verdict and notes, the indicators (addresses, domains, URLs, file hashes), and the investigation's notes and pinned answers into one text you can copy or save.
- **The investigation** (*File → Investigation*, or the button in the status bar, which counts the pins) holds your notes and the answers you pinned (**📌 Pin** in Ask and in the host panel), with their tables and filters (**Show its packets**, **Ask again**). **Save investigation…** writes them, your verdicts and notes on the alerts and the focus you were working in to a small JSON file (no packets); **Open investigation…** puts them back. Verdicts find their alerts again by kind and addresses, since alert numbers can differ between readings. A file made on another capture says so and offers to open that capture (if its path is a capture file that exists) or to use it here anyway; a file from elsewhere is checked field by field, cut to size and stripped of control characters, never trusted.

### Analyst tools

- **Save capture…** (top bar, and **Save packets…** in the Packets tab) writes a .pcap of every packet, only the packets the packet list is showing (its display filter, capture filter or alert scope), or only the packets you marked (Ctrl+M), like Wireshark's *File → Export Specified Packets*. A live capture saves everything recorded so far, while it keeps running. The saved packets are exactly the ones Wireshark selects with the same filter.
- **Share-safe copy** (*File → Save share-safe copy…*, or the option in the Save dialog) writes a copy to hand to someone else (a colleague, a vendor, a forum): the same conversations, packet sizes and timing, with every address replaced by a stand-in and what the packets carried cut away. Stand-ins are consistent through the copy (one device is one stand-in in every packet, ARP and ICMP included, and never its own address) and keep the network's shape: a private address stays private and in the same stand-in subnet as its neighbours (prefix-preserving, like Crypto-PAn), `.0` and `.255` stay network and broadcast, IPv6 keeps link-local and the host part a device uses on every network, MACs become locally administered ones, and multicast, broadcast and loopback addresses are kept. Contents are cut after each packet's TCP/UDP/ICMP header (tunnels, IP options with addresses and IPv6 routing headers too), the original lengths stay in the file, and checksums are recomputed where nothing was cut, so Wireshark reads the copy without a single error. Optionally keep what the packets carried (only the addresses change, checksums recomputed for the stand-ins; names and addresses inside the data stay) or hide the date (the copy starts at 1 January 2000). Every copy draws a new random key, so two copies can't be matched up; the **address key** (which stand-in is which real address) is offered as a separate download for you to keep. Packets of link types that can't be rewritten (802.11, PKTAP) are left out and counted. On the demo capture Wireshark's conversation tables of the copy match the original's row for row, with no real address or readable text left in the file.
- **The command bar** (top of the window, Ctrl+K) takes anything and does it, saying what it will do as you type: a packet number (`1234`, `go to 1234`) goes to that packet; `find password` fills in and runs Find; an address or MAC opens its host panel; a display filter (`dns`, `ip.addr == 10.0.0.5`; field names come from the filter catalog, so `zoom.us` is a question, not a field) is applied to the packet list; `what to look at first` lists it; anything else is asked of the capture. ↑ ↓ go back through what you typed (kept in this browser only).
- **Applications** (*Statistics → Applications*; also in the host panel and in Ask: "what is using the bandwidth?", "who uses Zoom?", "what apps did 10.0.0.12 use?") groups the connections into the applications people recognise, about 60 of them (Zoom, Teams, Slack, Microsoft 365, YouTube, Netflix, Spotify, Windows and Apple updates, Dropbox, GitHub, Steam…) in kinds (video calls, streaming, software updates, messaging, cloud storage…), named from the TLS server name, the HTTP Host or a name a DNS answer in the capture gave the server's address, and otherwise by protocol or port (SSH, file sharing, printing, VPN, DNS). It shows how the data splits by kind, each application's data each way, devices and connections (a row opens its packets or the devices that used it), and one device's applications.
- **Device personalities** (*Analyze → Device personalities…*, **Personalities…** in the Hosts tab, or type `personalities`) sum up each device on the network in one sentence: what it is, what it mostly does (from its applications), which way its data flows, how many hosts it talks to and what it answers on, for example "A computer (macOS) that joins video calls, chats and browses the web; it mostly downloads; it talks to 21 hosts, 20 on the internet." **Remember these as normal** keeps the profiles (in the data folder, readable only by you; devices are recognised by a MAC that belongs to them alone, otherwise their address), and later captures show what each device does differently: a new kind of traffic (remote access, file sharing, a VPN…), a service it started answering on, local hosts it never talked to, much more data leaving, new devices and devices not seen. Each change opens the packets that show it; changes worth a look appear in *What to look at first* and in the host panel, which also shows the sentence. Devices in high or critical alerts (not marked as false positives) are listed first, in red, marked **⚠ Malicious activity** with buttons for those alerts.
- **Network rules** (*Analyze → Network rules (tests and firewall)…*, **Rules** in the status bar, or type `rules`) is one list of rules about your network, one per line. Every rule is both a **test** (does this capture break it? the connections, hosts or files that do, each opening its packets) and a **firewall rule** (enforced together with the others: what would be blocked). Write them in plain words or paste firewall lines; **What can I write?** lists every form with examples you click to add (and a search), **Add a rule ▾** offers them by topic, and a line that can't be read says why and offers the closest forms (*Did you mean block telnet?*). Typing a rule in the command bar (`block 10.0.0.5`, `don't let ubuntu hosts on the network`) opens the rules with it added, and **Block it…** in the host panel and on the map's host menu adds `block <its address>`.
  - **Block things:** `block 10.0.0.5`, `block 10.0.0.0/24`, `block example.com`, `block China`, `block telnet`, `block port 4444`, `block smb to the internet`, `block 10.0.0.5 from the internet`, `block printers from the internet`, `block ubuntu hosts`, `block uploads of router configs`.
  - **Keep devices off the network:** `no ubuntu hosts on the network`, `don't let windows xp machines on the network`, `keep kali hosts off the network`, `no raspberry pi devices`, `no iot devices on the network`, `no unknown devices`. Hosts are recognised by what their traffic says: an operating system (Ubuntu, Debian, Fedora, Red Hat/CentOS, Arch, Kali, Raspberry Pi OS, Windows, Windows XP/7, macOS, iOS, Android, ChromeOS, Linux) from User-Agents, web Server headers, the Hosts tab's fingerprint and the update and connectivity-check hosts only that system contacts (an Ubuntu machine fetching from archive.ubuntu.com; browsing ubuntu.com proves nothing); a maker from the network card; a kind of device as the Hosts tab recognises it. Each host comes with the evidence, which traffic can fake.
  - **Files:** `don't let router configs be uploaded`, `no programs downloaded from the internet`, `no files uploaded to the internet`, `no database dumps uploaded`, `no file uploads over ftp`, `no scripts downloaded`. FTP transfers are read, so a router configuration is recognised by its content (Cisco, Juniper, MikroTik, OpenWrt, pfSense and others), not only its name; HTTP and SMB transfers by name, type and first bytes.
  - **Who may talk to whom, services, encryption, how much, when:** `10.0.0.5 cannot talk to 10.0.0.9` (either direction; `cannot connect to` counts only what 10.0.0.5 starts), `no traffic between 10.0.0.0/24 and 10.0.1.0/24`, `printers only talk to 10.0.0.0/24`, `ubuntu hosts cannot talk to the internet`, `no device connects to North Korea`, `only 10.0.0.1 answers DNS`, `only 10.0.0.0/24 may use SSH`, `nothing uses telnet`, `printers only use port 9100`, `all web traffic is encrypted`, `no passwords in clear text`, `no host uploads more than 100 MB to the internet`, `no host talks to more than 50 hosts`, `no traffic between 22:00 and 06:00`, `servers are never active on weekends` (your computer's time zone). Contractions can be typed without the apostrophe (`dont`, `cant`).
  - **Firewall lines** are ordered (the first matching line wins; pf: the last, unless `quick`), and allow lines make exceptions: plain firewall words (`block in tcp to any port 23`, `allow out to the internet port 443`, `default block in`), iptables (`-A INPUT/OUTPUT/FORWARD`, `-p`, `-s`, `-d`, `--dport`, `--sport`, multiport, `-P`), ufw (`ufw deny 23/tcp`, `ufw default deny incoming`), pf (`block in quick proto tcp … port {22 3389}`) and Cisco access lists (`access-list 101 deny tcp any any eq 23`, with the invisible deny at the end). Lines a dry run can't judge (jumps to other chains, address tables, negation) say why.
  - **Enforcing them:** choose where the firewall sits, at the border (between your network and the internet: traffic inside the network never crosses it) or on every device. The summary says how many connections would be blocked, which of the capture's alerts would be stopped, still get through, or stay inside the network, what would stop working by service ("DNS: 723 connections, 18 local devices"), and the blocked connections. Each rule says what enforcing it blocks, and when a firewall isn't enough: limits on bytes or hosts are tests only, keeping hosts off the network takes the switch or the Wi-Fi (802.1X, MAC filtering), and reading what a transfer carries takes a proxy or IPS (blocking FTP or TFTP stops those uploads outright). Nothing touches a real firewall.
  - Rules and where they are enforced are saved in the data folder and apply to every capture you open; the status bar says how the open one does, and broken rules appear in *What to look at first*.
- **Speed of light** (*Statistics → Speed of light*, or type `speed of light`) checks where each internet server can physically be. Nothing travels faster than light, so a TCP handshake can't come back sooner than light takes to reach the server and return: a server that answered in 6 ms is at most 900 km from where the capture was made. The engine times every handshake (SYN to SYN/ACK for servers, SYN/ACK to ACK for clients from the internet); when the country the server's network is registered in is entirely farther away than light allows, the server can't be there, and ANTA says so (a CDN, a cloud region, a VPN exit, or something on the path answering for it). Many far-registered servers answering from next door suggests a transparent proxy or security appliance. A world map draws how far the selected server can be and colours its registered country red when it is impossible. The claim is kept safe: light in a vacuum, the fastest handshake, and the registered country's nearest edge less a margin for the simplified borders (Natural Earth 1:50m, public domain, bundled). Where the capture was made defaults to the place your computer's time zone is named after; **Change…** picks another place, coordinates, or off.
- **Protocol spell-check** (*Statistics → Protocol spell-check*, or type `spell check`) holds every packet against the rules of its protocol's standard, like a spell-checker: 29 rules across IPv4, ICMPv6, TCP, UDP, DNS, HTTP, TLS, SMB and SSH. Each finding says what is wrong in plain words, which RFC section it breaks (paraphrased), and why it matters: headers no operating system builds (reserved bits, SYN+FIN, NULL and Xmas scans), spoofing (multicast or loopback sources, Neighbor Discovery from off the link), doors left open (Content-Length with Transfer-Encoding: HTTP request smuggling; HTTP/1.1 without Host), and versions the standards forbid (SSL 3.0, TLS 1.0/1.1, SMB1, SSH-1). **Show the packets** opens them; the first frames link straight to them. The engine counts every rule in one pass (`--count-filter`), and the statistics filter and focus limit it.
- **What to look at first.** With no alert open, the detail pane lists up to five findings, worst first, each with why it matters and its next step as a button: each device whose alerts tell a story (its worst alert and its host panel), accounts that logged in without encryption (account names in the logins view; passwords never), programs and scripts downloaded, and the largest upload to the internet that no alert covers. ANTA no longer opens an alert by itself; **What to look at first** above an open alert (and in the Analyze menu) comes back to the list.
- **Ask the capture** (the command bar, or *Analyze → Ask, filter or go to…*) answers questions in plain words from the capture itself, and shows the display filter and the tool behind each answer, so it also teaches the filter language. Questions about a host get its numbers: "who did 10.0.0.5 talk to the most?" lists its peers (data each way, packets, connections, services), and so do "what did 10.0.0.5 connect to", "who connected to 10.0.0.5", "where did 10.0.0.5 send the most data", "10.0.0.5's top destinations" and "what external hosts did 10.0.0.5 talk to"; "did 10.0.0.5 talk to 203.0.113.50?" says yes or no with the volume each way, when, and over which connections; "what is 10.0.0.5?" gives its profile (name, device, OS, MAC, when seen, traffic, services, location, alerts); and there are its ports and services, protocols, the names it looked up and sites it visited, how much it sent, when it was active, and where a public address is. Questions about the whole capture work the same way: the busiest hosts and conversations (by data, packets, connections or duration, most or least, internal or external, "top 10"), the busiest ports, protocols and domains, who used something ("who used SSH?", "did anyone visit example.com?"), the addresses a name resolved to, counts and an overview. Lists come as small tables whose rows open their packets, and each answer opens its Statistics tool on the same packets. Filter requests still become filters: "DNS from 10.0.0.5 in the first 5 minutes except mDNS" becomes `dns && ip.src == 10.0.0.5 && frame.time_relative <= 300 && !mdns`, shown phrase by phrase with how many packets match. It understands addresses, networks, MACs and the names hosts announced, ports, domains, file names, about 40 protocols and families, problems (retransmissions, resets, failed lookups, HTTP errors, slow responses), sizes, times ("after 10:05", "the last 2 minutes"), "except" and "besides", polite and chatty phrasings, and common slips ("tlak", "msot", "recieved": it says how it read them). Within a focus (selected packets) the answers count only those packets. A question that is already a display filter is used as one. Nothing is applied until you choose. The rules run on this computer; if a detection agent is set up with an AI model, **Ask *model*** sends it the question (never the capture, internal addresses as pseudonyms unless you allowed them) and its filter is checked by the engine before it is offered, at most 60 questions an hour.
- **Story** (the Alerts tab's **List / Story** switch) links each device's alerts into one story, in time order and attack stage (scouting the network, getting in the middle, malware delivered, calling home, spreading inside, data leaving), with a one-paragraph account ("10.0.0.23 received suspicious software (…) at 10:01, then started calling home (…) at 10:02 …"). A program copied to another device links the two stories. The worst stories come first; alerts marked false positive and shared cloud traffic are left out.
- **Files** lists every file the capture carries, like Wireshark's *File → Export Objects*: HTTP downloads (after removing chunked and gzip/deflate encoding), files read from or written to SMB2 shares, and FTP transfers in passive and active mode, with name, location, client and server, type (from the file's first bytes), size, SHA-256 and whether every byte was captured. **Save…** writes the file out byte for byte and checks it against its SHA-256. On the NSA Codebreaker capture it finds all three router backups, which Wireshark's own FTP export misses because the server is behind NAT.
- **Sweep indicators…** (above the alert table, and in the Analyze menu) sweeps the capture for a pasted list of indicators of compromise, the way threat reports print them (defanged `hxxp` and `[.]` included): IP addresses (optionally with a port), CIDR networks, domains (with their subdomains, and names reached through a DNS CNAME), URLs, SHA-256 file hashes, JA3 and JA4 fingerprints, and file names (`file:name.exe`). For each one it lists the sessions it appears in and where (destination address, DNS answer, TLS server name, HTTP Host, a transferred file…), the hosts involved and the alerts that mention it, with **Show packets** to open them. **Add from alerts** fills the list from the high and critical alerts. Nothing is looked up online.
- **Right-click anything** for what to do next with it, in place of the system menu (Look Up, Translate, Services). ANTA recognises what was clicked: an alert, a file, a host or a line on the network map, a packet, or, anywhere on the page, an address (with its port), a domain, a MAC address, a file hash, a JA3/JA4 fingerprint, a URL, a file name or selected text. The menu opens with a **quick look** at what ANTA already knows about it (the name it answers to, its role, OS and vendor, where it is, how many of your hosts use it, threat-intel listings, its alerts), then the next steps: for an address, **Host details** (the host panel) first, then its packets, its alerts (the alert table narrowed to it) and **Explain** in plain words; the file in Files, a sweep of the capture for it, and copying it or its filter. An alert's menu also marks it (investigating, confirmed, false positive), sweeps for its indicators, asks the detection agent and saves its packets; a packet's menu leads with Explain and Follow Stream and gives each address its own submenu. **Quick look…** opens everything on one card. The facts come from this capture's analysis only; nothing is looked up outside the computer. Text boxes keep the system menu (paste, spelling), and the menus work from the keyboard (the Menu key or Shift+F10, arrows, Esc).
- **Explain** turns a connection into plain words: what happened, why it most likely happened, and what to check next. Open it from a packet (right-click, or **Explain this connection…** in the packet detail), a row of Statistics → Conversations, or an alert (**Explain…** in its stream panel). It recognises:
  - connections refused (reset), unanswered (repeated SYNs), blocked (ICMP "administratively prohibited", with whether the router or the host said so), closed UDP ports, unreachable hosts and networks, and MTU problems;
  - TLS handshakes refused by the server (each alert translated: no cipher in common, old version, unknown server name) or by the client (an untrusted CA, as with TLS interception), and handshakes dropped after the Client Hello;
  - application errors: HTTP status codes, FTP replies, SMB status codes, Kerberos errors (wrong password, unknown user, clock skew…), LDAP results, and DNS NXDOMAIN, SERVFAIL, REFUSED and unanswered queries;
  - resets by either side, a receiver that stops reading (zero window), packet loss (retransmissions), gaps in the capture itself, slow handshakes, half-open (SYN-scan) connections, and hand-built packets with no TCP flags.

  Each finding names the frames it rests on (a timeline links every step to its packet), and says what the payload most likely is when no decoder knows it: TLS, SSH or HTTP on an odd port, an embedded program, Base64, commands typed into a remote shell, fixed-size records like a beacon's, or random-looking bytes from a custom encrypted channel. The packet detail starts with the selected packet in plain words: Wireshark's analysis flags ("ACKed unseen segment", "Previous segment not captured", "Window full"…) and any error code it carries, translated. It is rule-based and runs locally: no language model, nothing sent anywhere; when the packets don't say why, neither does it.
- **Threat-intelligence feeds** (*File → Settings…*): abuse.ch's Feodo Tracker (botnet C2 servers), URLhaus (malware URLs), ThreatFox (C2 addresses, domains, URLs and hashes), MalwareBazaar (malware hashes) and SSLBL (malware JA3 fingerprints), plus any list you import (one indicator per line, or a CSV). A feed is downloaded only when you press **Update**; it is then kept on this computer. Every session is checked against the enabled feeds as it is analysed (destination and source addresses with their ports, DNS names and answers, TLS server names and fingerprints, HTTP URLs, transferred files' SHA-256), and a match raises a **Known Malicious Indicator** alert: critical for a C2 address or a known malware file, lower for a fingerprint match. **Check this capture** matches an already analysed capture against feeds updated since. On the malware exercise, ThreatFox, URLhaus and MalwareBazaar list the downloaded EXE and ThreatFox lists the trojan's C2 server.
- **Protocol on an unexpected port:** the engine identifies each connection's application from its first bytes (about 45 protocols: TLS, SSH, HTTP, SMB, RDP, VNC, DCE/RPC, the databases, SOCKS, OpenVPN, WireGuard, QUIC, BitTorrent, IRC, mail protocols and more), whatever port it uses. SSH on port 80, or RDP on 8080, raises a **Protocol on an Unexpected Port** alert (high for remote-access protocols); flow logs and the inventory use the identified application too.
- **Host baselines:** each internal host's traffic is counted in 30-second buckets (bytes out and in, connections, distinct hosts and ports, applications). Once a host has six minutes of history, a bucket far above its own normal (median + 8 MAD and ten times its 90th percentile, above absolute floors), or its first use of SMB, RDP, SSH, a database or a tunnel, raises a **Deviation from Host Baseline** alert. A busy server and a quiet laptop each have their own normal.
- **Flow logs:** one line per connection, with Zeek `conn.log`'s fields (who, to whom, which application, bytes and packets each way, how it ended), plus DNS, TLS, HTTP, files and the GeoIP of both ends, in a daily file in your data folder. Kept for live captures by default (and for opened files if you choose), pruned by age and total size. **Save this capture's flow log…** in Settings writes the open capture's as one file.
- **Detector** (toolbar, and the **Detection** menu) switches, in one click, what looks at every session besides the rule-based detectors, which always run (see *Detection models and the agent*): the built-in Isolation Forest, an ONNX model you added, or the detection agent (Claude Opus, Sonnet or Haiku, OpenAI or Gemini with your API key, a model on your own computer or a hosted one through an OpenAI-compatible server, or your own program). Choosing an agent that isn't set up yet opens its setup at whatever it still needs; ANTA switches once that and your agreement to send it sessions are saved. Its last entry, *Add a model, agent settings…* (or *Detection → Detection settings*), adds models and holds the agent's settings.
- **Settings…** (top bar): flow logging and retention, the rolling capture buffer (segment size and how many older segments to keep), the recordings on disk (open any segment, or delete a recording), and the GeoIP table (its date, and a button to download the latest).
- **Export CSV** on the alert table, every Statistics table, the asset inventory, the file list and the sweep results. Cells that a spreadsheet would run as a formula are written as text.
- Everything saved goes through the native Save dialog in the app (or the browser's download in browser mode), and is prepared in the private runtime folder first.

On a public malware-traffic-analysis.net exercise (a Windows client infected through a `curl`-fetched EXE that then ran a remote-access trojan), ANTA raises two critical alerts: the EXE download (bare IP address, port 9000, command-line downloader), and the trojan's custom protocol on port 443. The incident report gives the victim's IP, MAC, host name, user account and the EXE's SHA-256, matching the exercise's answer key.

On the NSA Codebreaker 2025 network-forensics task (three OpenWrt routers, and the question "which IP addresses are assigned to the malicious device?"), ANTA raises a critical **Poisoned DNS Answers** alert: one router answered `archive.ubuntu.com` with an address reserved for documentation (RFC 5737), where the other two routers gave Ubuntu's real addresses. The router backups uploaded over FTP in the same capture describe that router, so a critical **Compromised Device** alert names router3 and its row in the alert table lists all three of its addresses (LAN, the link to the next router, and an unusual loopback that never appears on the wire), which is the task's answer; the incident report lists them too. A client's hand-built TCP segments (no flags at all) to the false address are a second critical alert, and the configurations sent unencrypted to an anonymous FTP server are medium ones.

### What the demo capture contains and what ANTA reports

The demo is 10 minutes of traffic from 14 IPv4 hosts and 2 IPv6 hosts. It includes browsing, streaming, a Slack-style websocket keep-alive on 9 hosts, an endpoint agent checking in every 45 s on 9 hosts, software downloads, email attachments, video calls, IMAP IDLE and SSH. Five attacks are planted in it:

| Scenario | Severity | ANTA's explanation (abridged) |
|---|---|---|
| HTTPS C2, new connection every 4.2 s ±0.4% → 192.168.1.105:443 | critical | "High-confidence automated beaconing detected to 192.168.1.105:443. Connection occurs every exactly 4.2 seconds with < 1% variance, characteristic of a C2 sleep cycle." |
| HTTPS C2, 25 s sleep with **±20% random jitter** → 45.77.12.34:443 | critical | "...every ~24.4 seconds with ±17% symmetric jitter..., characteristic of a C2 sleep cycle with configured jitter." |
| HTTP C2 inside **one** keep-alive connection, every 15 s | critical | "...The client checks in over a single persistent connection every exactly 15.0 seconds..." |
| 260 base32 TXT queries under `exfil-cdn.net` | high | "...260 unique subdomains averaging 61 characters with 4.62 bits/char of entropy..." |
| 5.9 MB one-way upload to a destination no other host uses | high | "...5.9 MB uploaded in 4.6 s while only 3.0 KB came back (100% outbound)..." |
| Slack keep-alive (7 hosts) / EDR check-in (12 hosts): benign, perfectly periodic | low | "Periodic traffic to wss-primary.slack.com ... from 7 internal hosts ... typical of software heartbeats" |

The benign hosts raise **no** critical, high or medium alerts. One benign email attachment is flagged by the model as a statistical outlier, but at low severity, because other hosts use the same mail service. On a separate held-out benign capture (15 min, 22 hosts, 3,679 sessions), the whole system raises zero critical, high or medium alerts.

## Security and privacy

ANTA handles raw traffic, so it is built to keep that data local and private.

- **The desktop app exposes nothing to the network.**
  - The dashboard is served only on `127.0.0.1`, on a random port, with a fresh token on every launch. The native window gets that token directly and it is never shown.
  - Files and live captures run the engine as a child process. Records come over its stdout pipe, which no other process can reach, and closing its stdin stops it cleanly on every OS.
  - When elevation is needed (macOS/Linux), the OS's own prompt starts the engine as root. The engine opens the device, then drops to your account immediately. That account is taken from the app's real user ID, not from environment variables, and ANTA refuses to elevate on behalf of root. Records travel over a per-session ZeroMQ socket in the private runtime directory.
  - An elevated engine isn't the app's child, so it watches the app's process (`--parent-pid`) and stops capturing within a second if the app exits or crashes without stopping it. It also watches its session's private socket, which the app removes when you press **Stop**: the capture ends within a second even if the stop signal never reaches it, and the app checks that the engine is gone (if it isn't, the status bar says so and quitting ANTA stops it).
  - ANTA refuses to elevate an engine binary that is group- or world-writable.
  - Requests that change state (start/stop capture) must be JSON from the dashboard's own origin. Plain cross-site form posts are refused.
  - Opened files must start with pcap/pcapng magic bytes, and live interfaces must come from the engine's own device list, so request fields can't smuggle in arbitrary paths or shell input.
  - Raw packet bytes (the packet viewer) come only through the authenticated API.
  - All decoding of hostile bytes happens in the fuzzed C++ engine, not the browser.
  - Packet-view queries run the engine without a shell, with argument-validated filters, a concurrency cap and a timeout.

- **The dashboard requires authentication.** It binds to `127.0.0.1` by default. A random per-run token is printed once, at startup only. Opening the printed URL swaps the token for an `HttpOnly; SameSite=Strict` cookie and strips it from the address bar. Every API, WebSocket and export request needs that token. Use `--token` or `$ANTA_TOKEN` to set a fixed one.
- **Browser-side attacks are blocked.**
  - A Host-header allowlist defeats DNS rebinding: unknown hosts get `421`.
  - WebSocket `Origin` must match the host, so a page in another tab can't open a cross-site socket.
  - Strict CSP (`default-src 'none'; script-src 'self'`, no inline script), `X-Frame-Options: DENY`, `nosniff`, `no-referrer`, `no-store`.
  - All network-derived strings are rendered as text, never as HTML.
- **TLS key logs are treated as secrets.** A key log loaded for decryption holds the keys to the user's own TLS sessions; ANTA stores it owner-only (`0600`) in the private runtime directory, never writes its contents to a log, and deletes it when the user clears it or the app exits (a plain `kill` of `anta serve` exits cleanly too; one left by an app that was killed outright is removed at the next start). It is only ever used to decrypt, by the local engine, and never sent anywhere.
- **No external requests unless you ask.** The dashboard loads no CDN, fonts or telemetry, and lookups (GeoIP, feeds, fingerprints) are made against local copies. The only downloads are the ones you start: **Update** in the feeds panel (abuse.ch, over HTTPS) and **Download the latest table** in Settings (iptoasn.com, over HTTPS); both are size-capped and replace the local copy. The one thing that sends traffic details out is the detection agent, and only if you choose an AI provider as the agent and tick *Send the sessions it reviews to …* for that provider (each provider has its own agreement).
- **The detection agent is opt-in and read-only.** With an AI provider (Claude, OpenAI, Gemini or an OpenAI-compatible server), each review sends one session's summary (addresses, ports, sizes, timing, TLS names, HTTP paths without their query strings) and the lookups the agent asks for, and nothing else. Internal addresses go as `internal-host-1`, `internal-host-2`, … (a fresh set for each review, so reviews can't be linked) unless you allow them, and are translated back in the answer. An hourly limit (30 by default) caps how many paid requests it makes. Each provider's API key is stored owner-only (`0600`) in the data folder, sent only to that provider in a request header, and never sent back to the page; an OpenAI-compatible server never gets another provider's key from the environment. Requests to OpenAI, Gemini and compatible servers are verified against the operating system's certificate store and never follow a redirect (which could carry the key elsewhere), and a compatible server reached over plain `http://` must be on this computer or the local network. Your own agent program can be named only in the config file, never from the dashboard, so the page can't be used to run a command. The agent's tools only read what ANTA already knows, and its verdict only raises or annotates an alert.
- **Pop-out windows sign in with single-use tickets.** The desktop app opens them itself; each gets a ticket that is good once, for a minute, and lets in only the views a pop-out can show (checked again on the server). The page asks the app for windows and for the system Open dialog through the dashboard's own authenticated API: pywebview's script bridge builds its functions with `eval`, which the dashboard's Content Security Policy forbids, so it isn't used.
- **Added models are checked before use.** An ONNX file is loaded by ONNX Runtime with the CPU provider only (no custom-operator libraries), must take ANTA's 10 session features and give one finite score per session, and is stored owner-only.
- **IPC endpoints are private.** They live in `~/.anta/run` (mode `0700`) and are created `0600`, so other local users can't inject fake records or read the stream. A non-loopback `tcp://` ZeroMQ endpoint triggers a warning, because ZMTP's NULL mechanism is unauthenticated.
- **The engine runs with least privilege.**
  - It drops root right after opening the capture device: to `--user NAME`, or else the account that ran `sudo`. Untrusted packets are parsed unprivileged.
  - It sets `umask 077`, so recordings, stream dumps and exports are owner-only. A root-created recording is `chown`ed to the dropped-to user.
  - The binary is built with stack protector and `_FORTIFY_SOURCE`, plus PIE, RELRO, BIND_NOW and a non-executable stack on Linux.
- **Hostile input can't exhaust resources.**
  - Flow state has a global memory budget (`--max-memory-mb`, default 512). The least-recently-active flows are finished early (and still reported) when it's exceeded.
  - Out-of-order buffers count per-segment overhead, so floods of tiny segments hit the cap too.
  - Half-open TCP flows (scans, SYN floods) time out in 30 s.
  - Recordings rotate (`--write-max-mb`, default 1024, and `--write-keep`, default one `.1` generation); the app records live captures as a rolling buffer of 256 MB segments, keeping 8 older ones (Settings changes both).
  - The analyzer validates every record's types and ranges. Records may come from untrusted telemetry on stdin.
- **Exports are restricted.** They read only capture files named on the command line or announced by the engine over the private IPC channel. The file must start with pcap/pcapng magic, only the alert's own 5-tuples are extracted, and temp files are `0600` and deleted after two minutes.
- **Saving files.** What the page saves (packets, transferred files, tables, reports) is written owner-only into the private runtime folder, offered under an unguessable link that still needs the session cookie, and deleted after 15 minutes. File names coming from the network are reduced to a plain name (no folders, no device names, no control characters). Extracted files are never opened or run.
- **Optional redaction.** `--redact` strips query strings from HTTP URIs in metadata and leaves the contents of small text files sent over FTP out of it.
- **Explain with AI sends evidence, never packets, and only when asked.** The page shows the exact text first; secrets (passwords, base64 credential lines, query strings, cookies, long tokens) are stripped from every line and internal and hardware addresses are pseudonymised unless you allowed them; tests check a known password and the lab's internal addresses never reach the provider. It needs a provider you agreed to send data to, and shares the hourly cap of 60 requests with Ask the capture.
- **Passwords seen in traffic are never kept.** The cleartext-login report reads a password, Basic credential, form field, bind password or SNMP community only to know one was sent; the engine drops it at once, and only the account name and whether it was accepted reach records, alerts, reports or the page (the tests check a known password appears nowhere in the output).
- **Share-safe copies hide addresses with a fresh random key each time** (from the operating system's random source); the address key is written owner-only and offered separately, never put in the copy.
- **Verification.** Mutation fuzzing under AddressSanitizer and UndefinedBehaviorSanitizer (`make fuzz`) covers the dissectors (Kerberos, the Windows browser and DTLS included), reassembly, the DNS, HTTP and TLS parsers, QUIC decryption, HTTP, SMB2 and FTP file tracking and gzip/deflate decoding, the cleartext-login reader, the share-safe copy's rewriter (contents cut and kept), the ARP parser the LAN-spoofing detector uses, TLS 1.2 and 1.3 record decryption for every supported suite, display-filter fields and matching, and the filter parser itself: a 10-minute run pushed 125M mutated frames (2.6M multi-packet cases) through them with no findings. The Clang static analyzer is clean on all engine sources. `ruff` with bandit rules is clean apart from generator-only RNG use. Dependencies are installed from a lockfile with SHA-256 hashes.

**What remains:**
- The dashboard is plain HTTP. On a shared or remote host, keep it on loopback and use an SSH tunnel; `--allow-host` lets a tunnel hostname through.
- The token appears once in your terminal. Treat that line like a password.
- Exports and recordings contain full packet payloads, which can include credentials sent in cleartext. Handle them accordingly (or save a share-safe copy to pass on).

## Components

### C++ engine (`engine/src`)
- **capture.cpp** has two packet sources.
  - libpcap: live or file, with BPF and immediate mode.
  - Linux `TPACKET_V3 PACKET_RX_RING`: memory-mapped and walked in place, with no copy or syscall per packet. BPF is attached in the kernel with `SO_ATTACH_FILTER`.
  - Recordings rotate. `--extract` accepts several inputs, e.g. the rotated recording and the current one.
- **headers.h / packet.cpp** parse Ethernet (802.1Q/QinQ), Linux SLL, BSD loopback, IPv4 (detects fragments), IPv6 (walks extension headers), TCP and UDP, all bounds-checked.
- **flow.cpp** keys flows by the canonical 5-tuple. It hashes every HTTP response body with SHA-256 as it streams past (Content-Length, chunked or until close, gzip/deflate decoded by **inflate.cpp**), and records the first bytes each side sent so a protocol can be told apart from its port.
  - **smbfiles.cpp** follows SMB2 sessions (trees, opens, reads, writes) and hashes each file copied to or from a share; **ftpfiles.cpp** reads FTP control connections (the login, whether TLS was refused, each PORT/PASV/EPRT/EPSV) and hashes the file on the data connection each one announces, keeping a small text file whole so its contents can be read; **quic.cpp** (with **crypto.cpp**: HKDF, AES-128-GCM, checked against the RFC 9001 and NIST test vectors) reads the Client Hello from QUIC Initial packets, so QUIC sessions carry their server name and JA4 too.
  - **tlskeys.cpp** reads the TLS key log you load; **tlsdecrypt.cpp** (with **crypto.cpp**'s SHA-1, AES (both directions), GCM, CCM, ChaCha20-Poly1305 and the TLS PRFs, and **blockciphers.cpp**'s Camellia, ARIA, SEED, Triple DES and RC4, whose tables `cipher_tables.inc` is generated from the RFCs) opens one record of any supported suite; **tlsstream.cpp** decrypts a connection's two byte streams for the session analysis, following key updates, renegotiations and early data, and finding its place again after a capture gap.
  - Reassembly uses signed 32-bit sequence deltas, so it is correct across wraparound. It handles out-of-order segments, partial overlaps, retransmissions and zero-window, and holds everything to a global memory budget.
  - Each flow buffers only as much stream as its protocol parser needs. TLS buffers are released as soon as the hello parses.
  - Each flow keeps an uncapped 64-bucket throughput histogram whose buckets double in width as the flow ages.
- **inspect.cpp** is the packet viewer's decoder. It mirrors Wireshark's TCP sequence analysis and PDU reassembly (`desegment_tcp`), its TLS/HTTP/SSH dissection rules and its Info-column semantics, and runs two passes for files: the first records look-ahead cross-references, the second formats the requested page. It produces full layer/field breakdowns with byte offsets, and is fuzzed (in both single- and two-pass use) with invariants: every highlight range stays inside the frame, and every output string is valid UTF-8 JSON.
- **dpi.cpp** identifies a connection's application from the first 64 bytes each side sent (TCP and UDP signatures), knows each port's usual application, and tells which pairs are compatible (NetBIOS name service and DNS share a format; TLS on a mail port is normal).
- **dfilter.cpp** compiles Wireshark display filters (comparisons, `in` sets and ranges, `contains`, `matches`, slices, bitwise tests, CIDR) and matches them against the fields inspect.cpp records for each frame, named as Wireshark names them. Coloring rules use the same engine.
- **stats.cpp** computes the Statistics tab, Expert Information included, as Wireshark's taps count it (outer packets only, not the copies quoted inside ICMP errors), plus the per-host evidence behind the network map, and Follow Stream.
- **proto.cpp** parses DNS (compression pointers, TXT sizes, A/AAAA/CNAME), HTTP/1.x, and TLS Client/ServerHello into JA3 and JA4, and the server's answer into JA3S and JA4S (DTLS hellos too, reassembled from their fragments, with JA4's DTLS prefix `d`). All four are cross-checked in the tests against an independent Python implementation of the spec; JA3 and JA3S also equal Wireshark's on every hello of the bundled and exercise captures (QUIC's included). Payload byte entropy is recorded per direction.
- **emitter.cpp** writes from a dedicated thread with a bounded queue.
  - Live capture drops and counts records if the analyzer lags. Offline input applies backpressure and never drops.
  - Transports: stdout, newline JSON over a Unix socket, or a self-contained **ZeroMQ ZMTP 3.0 PUSH** implementation. That last one is wire-compatible with libzmq/pyzmq `PULL` sockets and verified against them in the tests.

### Python analyzer (`anta/`)
- **analyzer.py** (with **filetypes.py**)
  - **Beacon:** activity bursts on a (client, server, port) channel, scored RITA-style. Bowley skew and MAD/median of the intervals give jitter tolerance; the share of intervals near the dominant period tolerates missed check-ins; check-in size consistency also counts.
  - **Shared periodic:** the same cadence from many hosts to one destination is folded into one low-severity alert.
  - **DNS tunnel:** subdomain entropy, length, uniqueness and TXT ratio per registered domain, with `arpa`/`local` allowlisted.
  - **Exfil:** large, one-sided uploads to rarely contacted destinations.
  - **Download:** executables and scripts fetched over plain HTTP, recognised by their first bytes. Bare-IP servers, unusual ports, command-line downloaders and names or types that hide what the file is raise the severity; vendor update and certificate servers are quiet. The alert carries the file's SHA-256.
  - **TLS port:** a TLS port (443, 8443, 993…) whose conversation doesn't start with a TLS record. A long, two-way session like that is reported as a probable remote-access trojan; SSH, HTTP or OpenVPN there as a tunnel.
  - **Poisoned DNS:** what every resolver answered for each name, compared. An answer no real host can have (documentation, benchmarking or reserved ranges) for a name other resolvers resolve publicly is critical: that resolver is redirecting its clients. An internal address where others give a public one is medium (split DNS or redirection), a sinkhole (`0.0.0.0`) low. A lab resolver that answers everything with test addresses, and names that never leave the network (`.local`, `.home.arpa`, …), stay quiet. Connections to the false address are added to the alert.
  - **Compromised device:** a device a configuration in the capture describes, caught as the actor in a serious alert (poisoned DNS, beaconing, a remote-access channel, hand-built TCP). One critical alert names it, says why, and lists every address it has, the one it acted from first and loopbacks last.
  - **Crafted TCP:** data in TCP segments with no flags at all (not even ACK), which no operating system sends: a raw-socket implant or covert channel. Critical when the address came from a poisoned answer, even if the answer is judged later.
  - **FTP file:** a program, a file of keys or secrets, or a device configuration sent over unencrypted FTP; **devices.py** reads configurations into the devices and addresses described above, line by line (the text comes off the wire, so no pattern can backtrack).
  - **SMB file:** a program or script copied over SMB2. Written to an administrative share (`ADMIN$`, `C$`), the way PsExec-style tools move to another machine, it is critical; written elsewhere, or disguised by its name, high; read from a share, medium. Logon scripts and group policy files read from SYSVOL/NETLOGON are routine and stay quiet.
  - **Anomaly:** the ONNX Isolation Forest score. It alerts at medium severity only when no other host uses the destination; low if a few do, or if it is a local Windows domain service (SMB, LDAP, Kerberos to a domain controller), which the model, trained on internet sessions, finds unusual but which is routine; nothing if it's widely used.
  - **ARP spoofing / gateway impersonation:** an IPv4 address claimed over ARP by more than one hardware address — ARP cache poisoning, the usual way a device sets up a man-in-the-middle on a local network by pretending to be the gateway. The engine tracks which MACs answer for each IP (bounded) and lists any conflict; the analyzer names the likely spoofer (the MAC answering for several addresses), excludes the virtual MACs that VRRP/HSRP/GLBP legitimately share, and says plainly that the addresses are there so you can block the device at your switch or router — ANTA only observes. Critical.
  - **Port / host scan:** a source whose connection attempts rarely complete a handshake, across many ports of one host (vertical) or many hosts on one port (horizontal). A SYN scan never finishes the handshake even on an open port, so a high no-handshake fraction over many distinct targets is the signal; ordinary fan-out completes its handshakes. An internal host scanning (lateral movement, or a worm) is high and flagged as the offender; an external scanner is medium.
  - **DGA (domain-generation algorithm):** a host asking for many distinct, random-looking registered domains that mostly do not exist (NXDOMAIN) — malware cycling through generated names to find its live C2. High average name entropy separates it from a run of typos or a stale search suffix; the one name in the batch that resolves is the likely C2. High.
  - State is bounded and expires.
- **intel.py** reads the threat-intelligence feeds (each abuse.ch format, and plain or CSV lists of indicators) into an index and matches sessions against it; **geoip.py** looks addresses up in the offline ip2asn table (582,000 ranges, loaded in the background in under a second); **eta.py** classifies encrypted sessions by shape; **baseline.py** keeps each host's history and judges every closed bucket against it; **assets.py** builds the inventory and the per-country and per-network totals; **flowlog.py** writes and prunes the flow logs; **settings.py** validates and stores the Settings choices.
- **train.py** trains on benign captures and **calibrates the threshold on a held-out benign set**. It checks ONNX/scikit-learn parity (max error about 4e-7) and records the metrics in `models/meta.json`, and writes `models/calibration.npz` (the held-out benign and labelled attack sessions added models are measured on).
- **modelstore.py** keeps the models you add (checked, calibrated, owner-only) and which detector is in use; **agent.py** is the detection agent (settings, pseudonyms, the review queue and its hourly limit, Claude and your own program), **agent_providers.py** its OpenAI, Gemini and OpenAI-compatible backends (over the standard library's HTTP client: no extra dependency), and **agent_context.py** answers its lookups from the analyzer's state. **quicklook.py** answers the right-click menus' quick look the same way (and from the capture's statistics and session index once read).
- **security.py**: private runtime directory, record validation, NaN-safe JSON.
- **server.py**: the authenticated dashboard and API described above. **packets.py** runs the engine for the packet list, filters, statistics and Follow Stream (no shell, validated arguments, a concurrency cap, timeouts, a small cache) and keeps the coloring rules. **netmap.py** turns the statistics into the labelled network map, with the evidence for every label.

### Detection models and the agent

The rule-based detectors (beaconing, DNS tunnels, exfiltration, downloads, scans, spoofing and the rest) always run. **Detection…** chooses what else looks at every session:

- **The built-in Isolation Forest** (below), the default.
- **An ONNX model you add.** It must take one float input of shape `[N, 10]`, ANTA's session features in this order: `log_duration, log_bytes_out, log_bytes_in, byte_asymmetry, size_entropy, iat_cv, log_iat_mean, log_mean_payload, log_packets, out_pkt_ratio` (`anta/features.py` computes them), and give a score per session. That can be an anomaly score (an Isolation Forest's `scores`), or the probabilities of a two-class classifier (class 1 malicious), as a tensor or scikit-learn's per-class maps. ANTA runs it on the 6,932 held-out benign sessions to set its alert threshold at the benign alert rate you choose (0.5% by default), works out which way its scores point from the 167 labelled attack sessions in the demo capture, and shows both rates before you switch to it. Alerts from it say which model raised them. Most of those attack sessions are C2 check-ins that look ordinary one at a time (the beaconing detector catches them from their timing), so the built-in model catches 1.2% of them (the exfiltration upload and the keep-alive C2 session), which is expected; a model trained on the demo capture scores well there without being better on your network.
- **A detection agent instead of a model.** It reviews the sessions no detector flagged that moved data to destinations few of your hosts use. It can look up what ANTA knows (who else talks to the destination, its DNS names, country and network owner, threat-intel matches, alerts, and the conversation's history and regularity) and answers *malicious*, *suspicious* or *benign* with its reasons and what to check next. A malicious or suspicious verdict becomes an alert (high or medium). On a pair a detector already alerts on, the verdict is attached to that alert instead, whichever came first. Any alert can also be sent to the agent from its detail view (**Ask the agent about this alert**). The agent is one of:
  - **Claude**, through the Anthropic API with your key (the SDK comes with ANTA; Opus 5.5 by default, or Sonnet or Haiku; low, medium or high effort). It uses read-only tools and answers in a fixed JSON schema; a refusal, a cut-off answer or a malformed one is reported as an error, never taken as a verdict. **Test the agent** sends one made-up session to a documentation address.
  - **OpenAI** or **Google Gemini**, with your API key for that provider, through their chat completions and generateContent APIs. **List models** asks the provider which models your key can use. The same read-only tools are offered (OpenAI's strict function calling, Gemini's function declarations), and OpenAI enforces the verdict's JSON schema.
  - **An OpenAI-compatible server**: a model running on your own computer or network through Ollama (`http://localhost:11434/v1`), LM Studio, llama.cpp or vLLM, or a hosted service such as OpenRouter, Groq or Mistral. Give its address (the dialog suggests the common ones), a model name (or **List models**) and, if it needs one, a key. With a model on your own computer, the sessions never leave it. Smaller models call tools less reliably, so with every provider other than Claude the session's own lookups (the destination, the host, the conversation's history) are sent with it up front; a verdict written in prose or a ```json block is read, a model that answers in prose first is asked once more for the JSON, and anything else is reported as an error.
  - **Your own program**, named in the config file (`agent_command = ["/path/to/agent", "--flag"]`). It gets one JSON line on standard input, `{"session": {...}, "context": {"destination": {...}, "host": {...}, "history": {...}}}`, and prints one JSON verdict, `{"verdict": "malicious|suspicious|benign", "confidence": 0.0-1.0, "headline": "...", "reasons": [...], "next_steps": [...]}`, within 60 seconds.

The choice, the added models and the agent's settings are kept in the data folder and survive restarts.

### Model quality (`models/meta.json`)
- **Training:** 19,692 benign TCP sessions (300 trees, 2,048 sessions per tree) from two synthetic offices: 31 hosts browsing, streaming, downloading, mailing, calling and checking in over 30 min, and 99 more over another 30 min, browsing at their own pace (light to heavy users) and doing the rest of an office's day: remote desktop, database connections, a file server (listings, opens, saves), API polling, software updates, cloud file sync, print jobs and web apps. The synthetic senders respect the TCP receive window and acknowledge data correctly, so large transfers have realistic timing.
- **Calibration:** 6,932 held-out sessions from two other seeds and host sets set the threshold at a 0.50% false-positive rate.
- **Held-out test:** 4,451 benign sessions from a third seed, never trained or calibrated on: 0.58% of them alert (the previous model, trained on 6,770 sessions, alerted on 0.76% of the same ones). The most unusual benign sessions are large two-way file-server sessions; an Isolation Forest isolates extremes quickly, whatever their kind.
- **Evaluation on the demo:** the model flags the exfil upload and the keep-alive C2 session (the beacon detector also raises the latter as critical). Raw session-level false positives are 0.38% (previously 0.46%); destination-prevalence context turns them into suppressions or low-severity notes rather than actionable alerts. Across random seeds, attack sessions rank above more held-out benign sessions than before (0.88 against 0.83, as the chance a benign session looks more ordinary than an attack one).
- **Retraining:** `make train` regenerates the captures, trains, calibrates, measures on the held-out set and the demo, and prints the current model's numbers on the same data next to the new one's (`--compare`); `meta.json` keeps both.
- **What the model doesn't catch:** individual beacon check-ins look like ordinary small HTTPS sessions and are *not* flagged by the model. That is deliberate, and it's why the timing detector exists.

## Known limits
- **Windows and Linux were cross-compiled and linked, not run.** On this Mac, the engine was cross-compiled with zig against the real Windows (MinGW) and Linux (glibc + kernel) headers, for x86-64 Windows, x86-64 Linux and arm64 Linux, with `-Wall -Wextra` and no warnings. It linked into complete Windows `.exe` and Linux ELF executables. The `AF_PACKET` ring was compiled against the real kernel headers. None of these were *run* here.
- **The Windows and Linux app packages have not been produced yet.** `.github/workflows/build.yml` builds them on native runners; it passes `actionlint` but hasn't been run, since the project isn't in a GitHub repository yet.
- **Live capture on Windows can't be tested in CI.** Npcap's free licence doesn't allow unattended installs, so the Windows CI job runs the server tests and a packaged-app smoke test without packet analysis.
- **The privileged paths haven't been exercised.** That covers the macOS admin prompt, Linux pkexec, and the engine's root drop: all need a real password prompt.
- **The macOS app was built and tested here.** The window loads and connects, file analysis runs end to end, interfaces are listed, and exports work.
- **The training and evaluation data is synthetic.** It comes from `anta/tools/gen_traffic.py` and is realistic at the protocol level: real handshakes, TLS hellos, reordering and retransmissions. Retrain and recalibrate on your own network (`anta train --benign … --validate …`). Public sets such as CTU-13 and CIC-IDS2017 plug into the same commands.
- **The AI agents haven't made a real API request yet.** OpenAI, Gemini and the OpenAI-compatible path are tested against stand-in servers that speak each API (tool calls, refusals, errors, redirects, model lists), and the compatible path was driven end to end in the dashboard against a local stand-in; no real provider or key was used. **The Claude agent hasn't made a real API request yet either.** The Anthropic SDK (2.0) is now in both hash-pinned lock files and bundled in the app; the agent's request (model, effort, structured verdict, strict read-only tools, server-side fallbacks), the tool loop, and the handling of refusals, cut-off and malformed answers are tested through that SDK against a stand-in for the API, but no key was used here.
- **Known false-positive sources:**
  - A legitimate poller on a *single* host (a monitoring agent, for example) is a beacon by definition. Allowlist it by CIDR in the config.
  - Destination prevalence is learned as traffic arrives, so the first minutes of a capture have less context.
  - A fleet-wide compromise that beacons from many hosts would be reported as low-severity shared traffic. The alert text says so explicitly.
- **DCE/RPC call parameters (NDR) aren't decoded**, apart from the endpoint mapper's. The packet list names every call as Wireshark does, but where Wireshark's own parser for a call fails and adds `[Malformed Packet]` (as it does for `lsa_OpenPolicy3`), ANTA doesn't. That is the only packet-list and Expert Information difference left on a real Active Directory capture (297 of 298 expert entries match).
- **ARP detection is behaviour-based, not a packet-list annotation.** The ARP Spoofing alert is raised from the whole capture's IP↔MAC bindings, in the analyzer. In the packet list, Wireshark additionally tags the individual gratuitous ARP with `(duplicate use of … detected!)` in its Info column; ANTA's ARP row shows the `X is at Y` line without that suffix. The detection ANTA reports is the stronger, capture-wide form; only the per-frame cosmetic note is absent. ARP spoofing is also IPv4-only (IPv6 uses Neighbor Discovery, not yet correlated this way), and a legitimate failover that is neither VRRP, HSRP nor GLBP will be reported for you to confirm.
- **Scan and DGA need enough of the pattern to be sure.** A scan is reported only after about 20 distinct targets with a high no-handshake fraction, and DGA after about 30 distinct random-looking NXDOMAIN domains; a slow scan spread thin over a long capture, or a handful of generated lookups, stays under the threshold (tunable in the config). A scan alert's packet export holds one representative flow, not every probe. These thresholds keep benign fan-out and ordinary failed lookups quiet: on both benign captures and the two real exercise captures, none of the three fire.
- **Files are extracted from plain HTTP, SMB2 and FTP**, and from HTTPS (HTTP/1.x) when you load a TLS key log for it (see *Decrypt your own TLS*); FTPS and SMB3-encrypted transfers can't be read, and attachments in mail (SMTP, IMAP, POP) and TFTP transfers aren't listed yet. A file with a gap in the capture is saved only up to the gap (the list marks it Partial).
- **Saved captures are classic pcap with microsecond timestamps.** Nanosecond timestamps and pcapng comments are not kept; frames of a second link type in a mixed pcapng file are left out (the save says how many).
- **Explain covers the failures in its tables.** An unusual vendor error code is reported as the code with its general meaning, and a proprietary payload is characterised (encrypted, structured binary, text, a known file type), not decoded. It explains up to 25 conversations and 4,000 packets at a time.
- **The indicator sweep matches what ANTA parses from each session** (addresses, ports, DNS, TLS hello, HTTP request lines, transferred files), not arbitrary payload bytes; search those with a display filter (`frame contains "…"`). File hashes are SHA-256 only, and a 32-digit hex indicator is treated as a JA3 fingerprint. Device configurations are read from FTP transfers (up to 64 KB, the size of any router backup); one fetched over HTTP or SMB is hashed but not read.
- **Ports Wireshark gives to protocols ANTA doesn't decode.** Wireshark registers dissectors on about 590 TCP ports; a payload on one of those ANTA doesn't know (SAP NI on port 40000, for example) shows as plain TCP data in ANTA where Wireshark tries that protocol. No such port appears in the captures checked.
- **Remote-access trojans are found by the shape of their traffic** (a TLS port carrying something that isn't TLS, long and two-way), not by family. One that tunnels inside real TLS looks like any other TLS session unless it beacons.
- **Parsing scope:**
  - The analysis engine counts IP fragments rather than reassembling them (the packet viewer does reassemble them).
  - The HTTP/TLS parsers only see the head of each stream direction (16 KB; 4 KB for HTTP responses); HTTP response bodies are hashed in full as they stream past (gzip/deflate bodies are decoded up to 8 MB compressed).
  - QUIC is followed through its Initial packets (the Client Hello); everything after the handshake is encrypted, so HTTP/3 isn't read.
  - **TLS decryption** (with a key log) covers every TLS 1.3 suite and the AES, Camellia, ARIA, SEED, Triple DES, ChaCha20, RC4 and NULL suites of SSL 3.0 and TLS 1.0-1.2, key updates, renegotiation, early data, and premaster-only key logs. Not decrypted: the export-grade (40- and 56-bit) suites, single DES, IDEA, RC2, GOST and Kerberos suites; DTLS records (DTLS is dissected, not decrypted); QUIC beyond the Initial packets. Those records stay shown as encrypted. RC4 can't pick up again after a capture gap (its keystream position is lost with the missing bytes). The Triple DES, RC4 and SSL 3.0 test sessions are built by `anta/tools/tls_record.py` rather than recorded, since OpenSSL 3 no longer makes them; Wireshark decrypting them is what shows they are right. HTTP/1.x and HTTP/2 inside decrypted TLS are dissected, indexed and checked. After a capture gap, HTTP/2 on that connection can't be read on (the HPACK table is lost with the missing bytes), and the packet view, like Wireshark's, stops decrypting that direction; the session analysis resynchronises (see above). A key log is read from the file you load; keys aren't given to live captures.
  - Timing inside one very long session stops growing after 2,000 packets. Throughput uses the uncapped histogram.
- **The packet list and exports of a live capture read its newest two segments.** Older segments of the rolling buffer stay on disk until they rotate out; open one from Settings → Recordings to analyse it.
- **Database decoding covers the common messages.** For SQL Server, the error and message tokens are read up to the first column metadata or row of a response (errors normally come first), and only in responses that fit one TDS packet; a TLS handshake split across several pre-login packets isn't reassembled. MySQL and PostgreSQL agree with Wireshark on every well-formed exchange tested, prepared statements and binary rows included.
- **Fingerprints and identification are evidence, not proof.** OS and IoT labels are weighed guesses with their reasons listed; a host that shows no fingerprint stays "unknown". Common TLS libraries share JA3 and JA4 values, so a fingerprint listed by a feed is a lead. JA4S has no Wireshark field to compare with; it is checked against the specification. GeoIP gives where a network's owner is registered, not where a server stands.
- **Feeds are only as fresh as the last Update,** and abuse.ch stopped updating SSLBL's JA3 list in 2021. Matching uses what ANTA parses from each session (as for the indicator sweep).
- **Baselines need history.** A host is judged only after six minutes of its own traffic, so short captures and the first minutes of a live capture raise no baseline alerts.
- **A second Active Directory capture (73,779 frames)** matches Wireshark on 73,756 rows in two-pass and 73,763 in single-pass view. The rest are QUIC packets Wireshark decrypts and ANTA shows as protected payload, TLS records Wireshark labels "Ignored Unknown Record" after a gap, and a trailing separator Wireshark leaves after some SAMR calls.
